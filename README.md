# GigaAMLowMemASR

Telegram-бот для распознавания речи с диаризацией спикеров и поддержкой длинных аудио/видео записей. Спроектирован под работу на слабом железе: длинные записи режутся на части и обрабатываются последовательно, ASR-модель загружается один раз и переиспользуется, диаризация подгружается лениво и выгружается между запросами.

## Зачем это

Обычный ASR-пайплайн с диаризацией требует GPU и гигабайтов RAM. Здесь тот же конвейер (GigaAM v3 + ONNX-диаризация) укладывается в **2.5 ГБ RAM без GPU** за счёт:

- **внешней нарезки** длинных записей (по умолчанию 900 с) — аудио в памяти не масштабируется с длительностью файла;
- **последовательной обработки** частей — без параллельных пиков;
- **ONNX-инференса** — без загрузки PyTorch в память;
- **ленивой загрузки/выгрузки** диаризационных ONNX-сессий;
- **батчинга embeddings** с уменьшением батча при нехватке памяти;
- **опционального int8-квантования** (`ONNX_QUANTIZATION`).

## Возможности

- распознавание аудио и видео через ONNX Runtime (CPU, при наличии — CUDA/CoreML);
- диаризация спикеров (ONNX segmentation + embeddings + clustering);
- обработка длинных файлов без OOM: чанкование + VAD-сегментация;
- Telegram-интерфейс: голосовые, аудио, видеозаметки, большие файлы через Telethon (MTProto);
- экспорт: TXT, таймкоды, SRT/VTT, Markdown;
- Docker-образ с лимитами памяти под слабый VPS.

## Требования

- Docker и Docker Compose
- токен Telegram-бота (`TELEGRAM_BOT_TOKEN`)
- для файлов > 20 MiB — `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` (Telethon)

`ffmpeg` и зависимости Python устанавливаются внутри образа — на хосте ничего, кроме Docker, не требуется.

## Запуск

1. Создайте `.env` в корне проекта:

   ```env
   TELEGRAM_BOT_TOKEN=your_token_here
   LOG_LEVEL=INFO
   ```

   Для больших файлов добавьте:

   ```env
   TELEGRAM_API_ID=123456
   TELEGRAM_API_HASH=your_api_hash
   ```

2. Соберите и запустите контейнер:

   ```bash
   docker compose up --build
   ```

   `docker-compose.yml` уже задаёт `mem_limit: 2.5g`, `memswap_limit: 4g` и `MALLOC_ARENA_MAX=2` под слабый VPS, а также тома для кэша моделей и сессии Telethon.

3. Остановка:

   ```bash
   docker compose down
   ```

## Ключевые настройки

| Переменная | Default | Назначение |
|---|---|---|
| `CHUNK_SECONDS` | `900` | Длина внешней части; `0` отключает нарезку (осторожно: RAM растёт с длительностью) |
| `ASR_SEGMENTATION_MODE` | `vad` | Внутренняя нарезка: `vad` / `overlap_chunks` / `fixed_chunks` |
| `ONNX_PROVIDER` | `auto` | `auto` → CUDA → CPU (CoreML на macOS) |
| `ONNX_QUANTIZATION` | — | int8-квантование, если задано |
| `DIARIZATION_EMBEDDING_BATCH` | `16` | Начальный батч embeddings, уменьшается при OOM |
| `AUDIO_PREPROCESSING_MODE` | `auto` (в боте фактически `off`) | Дополнительная очистка звука |
| `LOG_RSS` | `1` | Логирование current/peak RSS через `/proc` (Linux) |

## Структура

- `bot.py` — Telegram-бот: приём файлов, выбор режима, отправка результата
- `src/recognizer.py` — фасад: нарезка, последовательная обработка частей, склейка текста
- `src/core/processor.py` — пайплайн одного файла: конвертация → ASR → диаризация → экспорт
- `src/core/asr/` — ONNX ASR, VAD, чанкование, longform, таймстемпы
- `src/core/diarization/` — ONNX segmentation, embeddings, clustering, mapping спикеров
- `src/utils/` — конвертация аудио, кэш моделей, атомарная запись, временные файлы
- `Dockerfile`, `docker-compose.yml`, `requirements.txt` — сборка образа и зависимости

## Ограничения и заметки

- **Нарезка критична.** Если `ffmpeg` недоступен или нарезка не удалась, файл обрабатывается целиком — на многчасовых записях это путь к OOM. В образе `ffmpeg` установлен, но проверяйте, что нарезка реально срабатывает.
- **Метки спикеров не сквозные при диаризации по частям.** Диаризация выполняется на каждой 15-минутной части отдельно; `speaker_1` в разных частях не гарантированно один и тот же человек.
- **ASR-модель остаётся в памяти** всё время жизни процесса (включая простой); диаризационные сессии выгружаются после запроса.
- **Препроцессинг в боте отключён** (default `off` в `process_file()`), даже если `AUDIO_PREPROCESSING_MODE` задан в окружении.
- **Пиковый RSS не нормирован в коде** — измеряйте через `LOG_RSS` на своей конфигурации и подбирайте `mem_limit` по факту.

## Примечание

Проект рассчитан на контейнерную работу с GigaAM v3 через ONNX Runtime и оптимизирован под ограниченную память. Для стабильной работы на длинных записях убедитесь, что нарезка включена, а лимиты контейнера соответствуют замеренному RSS на вашей платформе.
